# 🏠 ДомКонтроль

**Проблемы дома — без потерянных сообщений.**

ДомКонтроль — бот в мессенджере **MAX** и веб-панель для управляющей компании (УК). Житель за минуту отправляет заявку о проблеме в доме, УК видит все заявки в одном месте с автоматическим приоритетом, а житель получает уведомление в MAX при каждой смене статуса.

> MVP для хакатона на платформе MAX. Работает «из коробки» без токена MAX: встроенный эмулятор `/demo` показывает весь сценарий жителя.

---

## Какую проблему решает

Сейчас жители сообщают о поломках по телефону, в личных сообщениях и в общедомовых чатах. В итоге:

- **сообщения теряются**: диспетчер не видит заявку, если она утонула в чате;
- **одна проблема дублируется десятки раз**: «не работает лифт» пишут 20 соседей;
- **житель не знает судьбу обращения**: увидела ли УК, занимается ли кто-то.

ДомКонтроль превращает хаотичные сообщения в **структурированные заявки со статусами и обратной связью**, прямо в мессенджере, который у жителя уже установлен.

## Что умеет MVP

| Житель (бот MAX / эмулятор `/demo`) | Сотрудник УК (`/admin`) |
|---|---|
| 🏠 Сообщить о проблеме за 5 шагов: категория → дом → подъезд → описание → фото | 📊 Статистика: всего / новые / в работе / выполнено |
| ✏️ Проверить и изменить заявку перед отправкой | 🔎 Фильтр по статусам |
| ✅ Получить номер заявки (№1027…) | 📄 Карточка заявки: описание, фото, житель, история |
| 📋 «Мои заявки»: карточки со статусами и история | 🔄 Смена статуса: Новая → Принята → В работе → Выполнена / Отклонена |
| 🔔 Уведомление в MAX при смене статуса | 🤖 Автоприоритет: Низкий / Средний / Высокий / **Авария** |
| ℹ️ Помощь, отмена на любом шаге | ♻️ Автообновление списка каждые 5 секунд |

## Архитектура

```
             ┌────────────────────┐        ┌───────────────────────┐
  MAX ──────►│ /api/max/webhook   │        │ /demo (эмулятор MAX)  │
  (вебхук)   │  parseIncoming…()  │        │  /api/demo/messages   │
             └─────────┬──────────┘        └──────────┬────────────┘
                       │  IncomingEvent               │ IncomingEvent
                       ▼                              ▼
             ┌─────────────────────────────────────────────────────┐
             │ lib/bot — логика бота (машина состояний диалога)    │
             │ engine.ts → report-flow.ts → texts / keyboards      │
             └─────────┬───────────────────────────────┬───────────┘
                       │                               │ OutgoingMessage
                       ▼                               ▼
             ┌───────────────────┐        ┌──────────────────────────┐
             │ lib/services      │        │ lib/max — MessengerAdapter│
             │ ticket-service    │───────►│  MaxAdapter (реальный API)│
             │ (создание, статус,│ notify │  MockMaxAdapter (демо-чат)│
             │  уведомления)     │        └──────────────────────────┘
             └─────────┬─────────┘
                       ▼
             ┌───────────────────┐   ┌───────────────────┐
             │ lib/repositories  │   │ lib/priority      │
             │ Prisma → SQLite   │   │ PriorityClassifier│
             └───────────────────┘   │ (правила → LLM)   │
                                     └───────────────────┘
  /admin (Server Components) ──► repositories / services
```

Ключевые решения:

- **Одна логика бота для MAX и для демо.** Эмулятор `/demo` не повторяет сценарий на фронтенде: он шлёт те же события в тот же `handleIncomingEvent()`, что и вебхук MAX. Разница только в транспорте: `MaxAdapter` или `MockMaxAdapter`.
- **Адаптер MAX изолирован** в `src/lib/max/`. Бизнес-логика знает только интерфейс `MessengerAdapter` (`sendMessage`, `sendNotification`, `answerCallback`) и функцию `parseIncomingMessage()`.
- **Приоритет через стратегию** `PriorityClassifier`. Сейчас это правила по ключевым словам и категории, позже можно подключить LLM без изменения остального кода.
- **Состояние диалога хранится в БД** (`BotSession`), поэтому бот переживает перезапуск сервера.
- **Ошибка уведомления не откатывает смену статуса**: сотрудник видит предупреждение, статус сохранён.

### 4. Запустить

Режим разработки:

```bash
npm run dev
```

Или production-сборка (быстрее и стабильнее для показа жюри):

```bash
npm run build && npm start
```

Откройте **http://localhost:3000**.

## Демо-режим

Демо-режим включён, если выполняется **любое** из условий:

- `DEMO_MODE=true` в `.env`;
- `MAX_BOT_TOKEN` не задан.

В демо-режиме:

- доступна страница `/demo`: эмулятор чата MAX с кнопками, отправкой текста и фото;
- `MockMaxAdapter` вместо отправки в MAX сохраняет сообщения бота в таблицу `ChatMessage`, а эмулятор забирает их опросом раз в 2 секунды;
- уведомления о смене статуса приходят в эмулятор.

Чтобы выключить эмулятор на боевом стенде:

```bash
DEMO_MODE=false
```

Демо-пользователи (id вида `demo-…`) и seed-жители всегда получают сообщения через мок, даже если токен MAX задан. Поэтому демо и реальный бот могут работать одновременно.

## Подключение MAX Bot API

### 1. Получить токен

Создайте бота на [платформе MAX для партнёров](https://dev.max.ru) и скопируйте токен из настроек бота.

### 2. Прописать переменные в `.env`

```bash
MAX_BOT_TOKEN=ваш_токен
MAX_API_URL=https://platform-api2.max.ru
MAX_WEBHOOK_SECRET=придумайте_длинную_строку
PUBLIC_URL=https://ваш-домен.ru
```

### 3а. Продакшен: вебхук

Приложение должно быть доступно по **HTTPS**. Зарегистрируйте вебхук:

```bash
npm run max:webhook
```

Скрипт вызывает `POST /subscriptions` с адресом `${PUBLIC_URL}/api/max/webhook` и секретом. MAX будет присылать события `message_created`, `message_callback`, `bot_started`, а секрет проверяется по заголовку `X-Max-Bot-Api-Secret`.

### 3б. Локально: long polling

Если публичного HTTPS нет, запустите рядом с `npm run dev` второй процесс:

```bash
npm run max:polling
```

Он забирает события через `GET /updates` и передаёт их той же логике бота. Если вебхук уже зарегистрирован, MAX не отдаёт события через `/updates`: сначала удалите подписку.

### Какие методы MAX используются

Все методы взяты из официальной документации [dev.max.ru/docs-api](https://dev.max.ru/docs-api) и сверены с официальным SDK [`max-bot-api-client-ts`](https://github.com/max-messenger/max-bot-api-client-ts):

| Метод | Для чего |
|---|---|
| `POST /messages?user_id=…` | ответы бота, уведомления (`notify: true`), инлайн-клавиатура `inline_keyboard` с кнопками `callback` |
| `POST /answers?callback_id=…` | подтверждение нажатия кнопки |
| `POST /subscriptions` | регистрация вебхука |
| `GET /updates` | long polling |

Авторизация идёт через заголовок `Authorization: <token>`. По документации передача токена в query-параметре больше не поддерживается.

## Приоритет заявок

`src/lib/priority/rule-based.ts` определяет приоритет так:

1. **Ключевые слова в описании** (важнее категории):
   - 🚨 **EMERGENCY**: пожар, дым, запах газа, искрит, затопило, застрял в лифте…
   - 🔶 **HIGH**: протечка, нет воды, нет отопления, нет света, лифт не работает…
   - ▫️ **LOW**: лампочка, паутина, грязно…
2. **Категория по умолчанию**: водоснабжение и отопление → HIGH, мусор и уборка → LOW, остальное → MEDIUM.

Причина выбора сохраняется и показывается сотруднику УК.

**Как подключить LLM:** реализуйте интерфейс `PriorityClassifier` (`src/lib/priority/types.ts`), например класс `LlmPriorityClassifier` с fallback на правила, и верните его из `getPriorityClassifier()` в `src/lib/priority/index.ts`. Остальной код менять не нужно.

## Ограничения MVP

- Один тестовый набор домов (ул. Тестовая, 10 и 12) из seed. Добавление домов через интерфейс в следующей итерации.
- Фото в демо хранятся локально в `data/uploads`. В реальном MAX сохраняется URL вложения из MAX.
- Панель УК без ролей: один общий доступ, опционально с паролем.
- Эмулятор `/demo` работает от лица одного демо-жителя.
